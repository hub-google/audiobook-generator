# 01 產品範圍與驗收標準

## 1. 產品目標

輸入一個支援的小說目錄網址及章節範圍，系統自動產出可播放、可續傳、具章節字幕與一致視覺的長篇有聲小說影片，並可發布為排序正確的 YouTube 播放清單。主要操作入口是 Windows Tkinter GUI；GitHub Actions 負責最多 20 個 worker 的並行產製與後續 YouTube 發布；本地命令列流程供開發與少量製作。

## 2. 使用者角色與主要情境

- 操作者：在 GUI 解析目錄、設定起訖章、排除非正文、啟動或取消雲端任務、查看進度。
- 維運者：設定 GitHub Secrets、檢查 Actions cache/artifact、處理 API 限額及重新執行失敗 jobs。
- 開發者：在本機執行單元測試、單機 pipeline 或指定 worker/stage，維護產物及 checkpoint 相容性。
- 觀眾：取得按 Part 排序、含硬字幕與可切換繁體中文字幕的公開 YouTube 內容。

## 3. 功能需求

### FR-01 目錄與選章

系統必須從目錄頁解析安全化書名、網站根網址、依頁面順序去重的章節 URL 與章名。章號採原目錄的 1-based 索引。起訖範圍為閉區間，排除清單不得導致剩餘清單重新編號。

### FR-02 任務設定與分工

系統必須產生 `config.yaml` 和 GitHub matrix。`chapters` 與 `selected_indices` 必須等長且位置一一對應。worker 以清單切片分工；若依指定章數會超過 20 個 worker，必須自動提高每 worker 章數。

### FR-03 逐章產製

每章依序完成爬取、清洗、語音與字幕、章節卡及影片。雲端每完成一個 stage 都必須驗證實體產物並原子保存 checkpoint；已完成且驗證仍有效的 stage 重跑時跳過。

### FR-04 分部

章節影片必須按章號排序，依 10～11 小時目標切為連續 Part。不得遺漏、重複或打亂章節；單章本身超過上限時允許單獨成 Part。合併使用暫存檔，成功驗證後才替換正式檔。

### FR-05 中繼資料與視覺

系統必須為每書快取一張無文字主視覺，為各 Part 產生獨立標題、描述、時間戳及低於 YouTube 2 MB 的 2560×1440 封面。正式內容不得出現 AI 免責聲明。

### FR-06 YouTube 發布

系統必須建立或沿用該書播放清單，依鎖定的 Part plan 發布。每 Part 的必要步驟為影片上傳、縮圖、CC 字幕、加入指定播放清單位置、改為要求的隱私狀態並驗證。任何中間失敗必須從 checkpoint 繼續，不得再次建立相同影片。

### FR-07 操作與觀測

GUI 必須顯示 workflow/job 狀態、逐章進度標記、YouTube 暫停或完成標記及可點擊網址；取消操作必須呼叫確定的 run ID。命令列與 Actions summary 必須能指出失敗章節及下一個續傳 stage。

## 4. 非功能需求

- 正確性：章節集合、順序、字幕時軸與音訊時長必須一致。
- 冪等性：重跑不得覆蓋有效成品、重複上傳影片或重複插入播放清單。
- 可恢復性：程序中斷後最多重做目前未完成 stage；已驗證 stage 保留。
- 可追溯性：checkpoint 記錄狀態、嘗試次數、時間、錯誤及產物指紋。
- 安全性：token、OAuth secret、ZIP 密碼不得寫入版本庫、log 或 artifact。
- 可攜性：Python 3.11；媒體處理依賴 FFmpeg/ffprobe；Windows 與 Ubuntu runner 均須支援。
- 效能：雲端最多 20 workers，`fail-fast: false`；逐章保存以降低大批次失敗的返工量。

## 5. 端到端完成定義

一個製作任務只有同時滿足以下條件才算完成：

1. `selected_indices` 的每章六個 stage 均由驗證器確認完成。
2. 所有 worker 成功且輕量 artifact 可取得。
3. Part plan 覆蓋每章一次、順序正確且已鎖定指紋。
4. 每個 Part 的 YouTube Video ID、縮圖、CC 字幕、播放清單位置及隱私狀態均已驗證。
5. `state.json` 狀態為 `complete`，completed 數量等於 Part plan 數量，無任何 pending 項目。

本地 `main_pipeline.py` 印出 `Pipeline Completed` 不等於上述端到端完成；它目前是「所有步驟皆已嘗試」訊息。

## 6. 最低驗收案例

- 選取 1～10 章並排除 3、7：輸出章號必須為 1、2、4、5、6、8、9、10。
- 中斷在第 2 章 TTS 後重跑：第 1 章所有 stage 跳過，第 2 章從 TTS 組開始，不重爬有效文字。
- 破壞既有 WAV 或 SRT：checkpoint 啟動時必須撤銷該 stage 及其下游完成狀態並重建。
- YouTube 影片已建立但縮圖遇 429：保存 Video ID，下次先補縮圖，不得新建影片。
- 播放清單已有相同精確標題：恢復對應 Video ID 或跳過，不得重複發布。
- 缺少必要生圖憑證且無有效 master cover：封面流程失敗；不得產生假稱 AI 圖的低品質備援。

## 來源網站缺章與部分發布驗收

- HTTP timeout、DNS、429、5xx、防機器人頁與內容解析異常必須維持可重試失敗，不得自動視為缺章。
- 同一章節網址連續三次成功取得相同 HTTP 200 空文章頁，且頁面不含防機器人特徵時，系統可標記為 `source_missing`。
- `source_missing` 是可接受的來源缺漏：不得生成假文字、靜音或空白影片；worker 必須以成功結束並在 Actions warning、Job Summary 與 JSON 證據中列出章號。
- Part 規劃必須忽略已確認的來源缺章，按其餘有效章節的實際 MP4 時長累積至 10–11 小時並合併。
- 沒有 `source_missing` 證據的缺檔仍須阻止完成狀態並由排程續作。
- 所有規劃 Part 完成影片、縮圖、CC 字幕、播放清單加入、公開狀態及最終回讀後，production run 才可成功；成功後排程不得再重跑。
