# 01 產品範圍與驗收標準

> 全系統最高驗收原則：品質不合格時只能重試或報錯停止；不得簡化、降級、猜測、產生通用替代內容或跳過錯誤繼續。詳細規範見總需求書首頁「最高優先級：品質不可妥協」。

## 1. 產品目標

輸入一個支援的小說目錄網址及章節範圍，系統自動產出可播放、可續傳、具章節字幕與一致視覺的長篇有聲小說影片，並可發布為排序正確的 YouTube 播放清單。主要操作入口是 Windows Tkinter GUI；GitHub Actions 負責最多同時 17 個 worker 的並行產製與後續 YouTube 發布；本地命令列流程供開發與少量製作。

## 2. 使用者角色與主要情境

- 操作者：在 GUI 解析目錄、設定起訖章、排除非正文、啟動或取消雲端任務、查看進度。
- 維運者：設定 GitHub Secrets、檢查 Actions cache/artifact、處理 API 限額及重新執行失敗 jobs。
- 開發者：在本機執行單元測試、單機 pipeline 或指定 worker/stage，維護產物及 checkpoint 相容性。
- 觀眾：取得按 Part 排序、含硬字幕與可切換繁體中文字幕的公開 YouTube 內容。

## 3. 功能需求

### FR-01 目錄與選章

系統必須從目錄頁解析安全化書名、網站根網址，以及依頁面順序保存（包括疑似重複項目）的章節 URL 與章名。選章視窗必須以六欄表格顯示「UUID、編號章節數、網站章節數正規化、網站顯示章節數、章節名稱、重複標記」，欄名中不得插入額外空格。此處 UUID 是目錄解析時依原始順序建立的 1-based 固定流水號 `1..N`，不是隨機字串；取消勾選、排除、搜尋、改名及「重新排序已選章節」均不得改變 UUID。

網站章節識別前綴中的中文數字、大寫中文數字、全形數字及分隔空格必須正規化為阿拉伯數字；`序章`、`楔子`、`番外`、`後記` 及季／卷／部／篇／集等結構文字必須保留，例如 `番外二` 正規化為 `番外2`、`第一季第一集` 正規化為 `第1季第1集`。正規化只可作用於已辨識的標題前綴，不得修改章節名稱內的數字。

重複判斷預設必須同時比較「網站章節數正規化」與「去除所有空白後的章節名稱」；GUI 必須允許操作者勾選其中一項或兩項，兩項皆選時採 AND 判斷，且不得允許零項條件。疑似重複項目仍須保留供使用者檢視或排除。

操作者必須能雙擊「章節名稱」儲存格原地編輯；Enter 或失焦保存、Esc 取消，空白名稱不得保存。修改後必須立即更新顯示、搜尋及重複分析，並以固定 UUID 為鍵保存到雲端任務。雲端重新解析目錄後必須再次套用改名資料，且 worker 寫入 RawText 的第一行及其後 Cleaner、TTS、字幕、章節卡與影片流程均須使用修正後標題，不得被網站原章名覆蓋。

「重複標記」欄中的「重複」文字必須可單擊。單擊後必須開啟明細視窗，顯示該重複關聯群組內每章的「UUID、網站章節數正規化、網站顯示章節數、章節名稱」；明細必須同時包含後續重複章及其撞到的原始章，跨多筆關聯時須列出完整連通群組。

網站來源索引採原目錄的 1-based 順序並持續用於下載定位。選章視窗必須提供「依網站章節正規化順序排列」、多選拖曳、上移、下移及還原原始順序；Ctrl/Shift 多選後移動時必須保持所選章節彼此的相對順序。無法辨識為純數字的正規化章號排在數字章號之後，相同章號必須使用移動前相對順序作穩定排序。

「編號章節數」是小說實際製作順序的唯一準則。操作者確認章節順序後，所有已選章節必須按目前排列連續編為 `1..N`；下載、RawText、Cleaner、TTS、字幕、章節影片、Part 合併、命名及發布皆必須依此順序，不得在任何後續階段改按 UUID、網站原始索引或網站顯示章號重排。UUID 只可用於定位原始網址、改名及排除對應，不得因拖曳而改變。

### FR-02 任務設定與分工

系統必須產生 `config.yaml` 和 GitHub matrix。`chapters` 與 `selected_indices` 必須等長且位置一一對應。worker 以清單切片分工；matrix 最多可建立 20 個 worker，但 GitHub Actions 同時執行數必須限制為 17；若依指定章數會超過 20 個 worker，必須自動提高每 worker 章數。

### FR-03 逐章產製

每章依序完成爬取、清洗、語音與字幕、章節卡及影片。雲端每完成一個 stage 都必須驗證實體產物並原子保存 checkpoint；已完成且驗證仍有效的 stage 重跑時跳過。

GUI 必須允許操作者為每本小說設定最多 100 條「刪除關鍵字」，每條最多 10,000 字元並可包含換行。每一條均為完整純文字，不是正則表達式；括號、方括號、句點、星號、問號、反斜線等符號必須視為普通文字。Cleaner 必須刪除章節中所有與設定逐字相同的片段，GUI 文字抽查預覽與雲端正式 Cleaner 必須呼叫相同清洗函式並產生相同結果。

### FR-04 分部

章節影片必須按章號排序，依 10～11 小時目標切為連續 Part。不得遺漏、重複或打亂章節；單章本身超過上限時允許單獨成 Part。合併使用暫存檔，成功驗證後才替換正式檔。

### FR-05 中繼資料與視覺

系統必須為每書快取一張無文字主視覺，為各 Part 產生獨立標題、描述、時間戳及低於 YouTube 2 MB 的 2560×1440 封面。正式內容不得出現 AI 免責聲明。

### FR-06 YouTube 發布

系統必須建立或沿用該書播放清單，依鎖定的 Part plan 發布。每 Part 的必要步驟為影片上傳、縮圖、CC 字幕、加入指定播放清單位置、改為要求的隱私狀態並驗證。任何中間失敗必須從 checkpoint 繼續，不得再次建立相同影片。

「使用者最後看到的播放清單」是發布成功的最後一關，不得以內部 checkpoint、上傳成功回應或標題集合取代。系統必須按 YouTube 回傳的實際位置完整讀回所有播放清單項目，且只有同時滿足以下條件才可完成：項目數恰好等於鎖定 Part plan；位置 0 至 N-1 對應第 1 部至第 N 部；每一部恰好出現一次且沒有遺漏；不得包含刪除、不可用或重複 Video ID。任何不符均須使 workflow 失敗。

所有 Part 封面必須一致。最終驗收必須計算並保存唯一封面 SHA-256；若發現差異，系統必須以最後一部實際使用的封面為唯一標準，重新呼叫 YouTube 縮圖 API 覆蓋播放清單內每一部影片（包含最後一部），並在本地同步為相同檔案。只有全部替換成功且雜湊一致後才可完成；任何影片無法替換、封面缺失或無法提供證據時，workflow 必須失敗，不得另外生成新圖。

播放清單在產製／發布尚未完成時不得填入推估時數，可使用不含時數的處理中標題。只有全部 Part 已完成、實際影片時長均已探測，且使用者播放清單最終驗收通過後，才可將標題更新為 `[已完結]《小說名稱》XX小時 全集`。`XX` 必須是全部 Part 實測秒數加總後除以 3600 的整數商（小數直接捨去），不得補前導零、不得依章數或預估時長產生。

### FR-07 操作與觀測

GUI 必須顯示 workflow/job 狀態、逐章進度標記、YouTube 暫停或完成標記及可點擊網址；取消操作必須呼叫確定的 run ID。命令列與 Actions summary 必須能指出失敗章節及下一個續傳 stage。

### FR-08 多小說雲端佇列

GUI 必須支援批量貼入目錄網址、保存順位、插入與移動、暫停、恢復、停止及刪除。正式清單保存於 GitHub `automation-state` 分支；GUI 關閉後 GitHub 調度器仍須逐部執行，下次開啟 GUI 必須從 GitHub 還原清單、順位、Run ID 與狀態。每部小說使用永久 `task_id`，不得以「最新 Run」猜測任務歸屬。

GUI 必須將尚未完成與嚴格成功完成的小說分成「進行中／尚未完成」及「已完成（Success）」兩份清單；兩份清單顯示相同欄位。只有 strict success gate 通過的 `completed` 任務可出現在 Success 清單，失敗、取消、等待重試、需人工處理及暫停任務均不得移入。

### FR-09 Hugging Face 完整備份

每個 10～11 小時 Part 必須將 MP4、實際上傳 YouTube 的同一份 SRT、Part manifest、YouTube metadata 與 ffprobe media info 保存至 private HF Dataset Repo；全書根目錄另存唯一 `master_cover.jpg`、來源設定、`part_index.json` 與 `book_manifest.json`。HF 與 YouTube 應並行，上傳與驗證狀態必須各自續傳。

## 4. 非功能需求

- 正確性：章節集合、順序、字幕時軸與音訊時長必須一致。
- 冪等性：重跑不得覆蓋有效成品、重複上傳影片或重複插入播放清單。
- 可恢復性：程序中斷後最多重做目前未完成 stage；已驗證 stage 保留。
- 可追溯性：checkpoint 記錄狀態、嘗試次數、時間、錯誤及產物指紋。
- 安全性：token、OAuth secret、ZIP 密碼不得寫入版本庫、log 或 artifact。
- 可攜性：Python 3.11；媒體處理依賴 FFmpeg/ffprobe；Windows 與 Ubuntu runner 均須支援。
- 效能：雲端 matrix 最多建立 20 workers，但任何時刻最多只允許 17 workers 執行，`fail-fast: false`；逐章保存以降低大批次失敗的返工量並保留其他 Actions runner 容量。

## 5. 端到端完成定義

一個製作任務只有同時滿足以下條件才算完成：

1. `selected_indices` 的每章六個 stage 均由驗證器確認完成。
2. 所有 worker 成功且輕量 artifact 可取得。
3. Part plan 覆蓋每章一次、順序正確且已鎖定指紋。
4. 每個 Part 的 Hugging Face MP4、SRT、manifest 與 media info 均已驗證，且全書總封面及索引存在。
5. 從 YouTube 完整讀回的使用者播放清單恰好包含鎖定的全部 Part，並嚴格由第 1 部排列至最後一部，無遺漏、重複、刪除或不可用項目；每個 Part 的 Video ID、縮圖、CC 字幕及隱私狀態均已驗證。
6. 所有 Part 的實際上傳封面完全一致；若曾有差異，已以最後一部封面覆蓋每一部影片，且 `state.json` 保存唯一封面 SHA-256、是否修復及標準來源 Part 的驗收證據。
7. `state.json` 狀態為 `complete`，completed 數量等於 Part plan 數量，無任何 pending 項目。
8. 播放清單正式標題符合 `[已完結]《小說名稱》XX小時 全集`，且 `XX` 可由鎖定 Part plan 內全部實測時長重算得到。
9. 佇列任務取得 `strict_success=true` 後才可標記 `completed` 並啟動下一順位。

本地 `main_pipeline.py` 印出 `Pipeline Completed` 不等於上述端到端完成；它目前是「所有步驟皆已嘗試」訊息。

## 6. 最低驗收案例

- 選取 1～10 章並排除 3、7：輸出章號必須為 1、2、4、5、6、8、9、10。
- 選取 1～10 章並排除 3、7，再執行「重新排序已選章節」：編號章節數必須為連續的 1～8，來源索引仍為 1、2、4、5、6、8、9、10。
- `第 １２ 三 章 2026年的約定` 必須拆成網站顯示章節數 `第 12 三 章`、正規化值 `123`、章節名稱 `2026年的約定`；名稱中的 `2026` 不得被正規化或移除。
- `番外二` 與 `第一季第一集` 必須分別正規化為 `番外2` 與 `第1季第1集`。
- 預設重複條件下，只有正規化章節識別與去空白章名皆相同的後續項目可標記重複；只選章節識別條件時，同章號但不同章名的後續項目亦須標記。
- 將包含 `(`、`.*`、`[公告]?` 及換行的完整文字加入刪除關鍵字後，GUI 預覽與正式 CleanText 必須只刪除完全相同片段；`.*` 不得被解讀為萬用匹配或清空正文。
- 目錄 UUID 241 在排除前面任意章節並重新排序後仍必須是 241；只有「編號章節數」可改變。
- 將 UUID 人工排成 `3、1、4、2` 後，「編號章節數」必須依序為 `1、2、3、4`；config 的 URL、worker 切片、RawText、TTS、影片、合併及上傳順序皆必須維持 UUID `3、1、4、2`，不得還原成 `1、2、3、4`。
- 雙擊 UUID 241 的章節名稱、修正並按 Enter 後，關閉再從雲端任務載入仍須顯示修正值，worker 的 RawText 第一行也必須是修正後完整標題。
- 單擊任一「重複」文字必須開啟明細框，且同時列出被標記章與原始相撞章的 UUID、正規化章號、顯示章號及名稱。
- strict success 任務只出現在「已完成（Success）」；其餘終止或等待狀態仍只出現在「進行中／尚未完成」。
- 中斷在第 2 章 TTS 後重跑：第 1 章所有 stage 跳過，第 2 章從 TTS 組開始，不重爬有效文字。
- 破壞既有 WAV 或 SRT：checkpoint 啟動時必須撤銷該 stage 及其下游完成狀態並重建。
- YouTube 影片已建立但縮圖遇 429：保存 Video ID，下次先補縮圖，不得新建影片。
- 播放清單已有相同精確標題：恢復對應 Video ID 或跳過，不得重複發布。
- 全部 Part 實測總長為 327 小時 48 分鐘：最終標題必須是 `[已完結]《小說名稱》327小時 全集`；不得寫成 `0327小時`、`328小時` 或在尚未完成時先填時數。
- 使用者播放清單有多一項、少一項、任一 Part 亂序、相同 Video ID 重複，或含已刪除／不可用項目：最終驗收必須失敗。
- 任兩個 Part 封面 SHA-256 不同：必須以最後一部封面覆蓋全部影片；全部替換後仍不一致或任一替換失敗，最終驗收必須失敗，且不得重新生圖。
- 缺少必要生圖憑證且無有效 master cover：封面流程失敗；不得產生假稱 AI 圖的低品質備援。

## 來源網站缺章與部分發布驗收

- HTTP timeout、DNS、429、5xx、防機器人頁與內容解析異常必須維持可重試失敗，不得自動視為缺章。
- 同一章節網址連續三次成功取得相同 HTTP 200 空文章頁，且頁面不含防機器人特徵時，系統可標記為 `source_missing`。
- `source_missing` 是可接受的來源缺漏：不得生成假文字、靜音或空白影片；worker 必須以成功結束並在 Actions warning、Job Summary 與 JSON 證據中列出章號。
- Part 規劃必須忽略已確認的來源缺章，按其餘有效章節的實際 MP4 時長累積至 10–11 小時並合併。
- 沒有 `source_missing` 證據的缺檔仍須阻止完成狀態並由排程續作。
- 所有規劃 Part 完成影片、縮圖、CC 字幕、播放清單加入、公開狀態及最終回讀後，production run 才可成功；成功後排程不得再重跑。
