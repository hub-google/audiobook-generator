# 06 部署、維運與故障處理

## 1. 開發環境

- Python 3.11。
- `pip install -r requirements.txt`。
- 系統可執行 `ffmpeg`、`ffprobe`；Windows 可使用 PATH 或專案預期的本地執行檔位置。
- 安裝可顯示繁體中文的字型；repository `fonts/` 為設計字型來源。
- GUI 需 Tkinter（一般 Windows Python 發行版內建）。

常用驗證：

```powershell
python -m unittest discover -s tests -v
python src/worker_pipeline.py --stage validate --worker-id 0
```

目前測試涵蓋產物驗證、pipeline checkpoint、publication checkpoint、TTS 語速相容性與 YouTube Part 規劃。新增狀態欄位、檔名或重試分類時必須擴充測試。

## 2. GitHub 設定

repository 必須有 Actions write/content write 權限、Packages read/write 權限及前述 secrets。workflow 固定 checkout dispatch 的 branch/ref；GUI 現行使用 `master`，若預設分支改名必須同時修改 GUI。runner 是 `ubuntu-latest`，production jobs 在 `ghcr.io/hub-google/audiobook-worker` 的固定 digest job container 內執行。

### 2.1 Worker image 發布契約

- `Dockerfile.worker` 是雲端 runtime 的唯一系統依賴來源；`requirements.txt` 是 Python 依賴來源。
- `build-worker-image.yml` 在上述檔案推送至 `master` 時建置 image，發布 `v1` 與 Git commit SHA 兩個 tag。
- image 建置成功後，`audiobook.yml` 必須使用建置 log 產生的 `sha256` digest；不得直接使用可變的 `v1` tag 執行 production。
- image build 必須執行 `ffmpeg -version`、`fc-match :lang=zh` 與 `gh --version`；任一驗證失敗不得發布。
- `audiobook.yml` 必須有 `packages: read`；image workflow 必須有 `packages: write`。私有 package 由 `GITHUB_TOKEN` 認證。
- 日常 production run 不得執行 `apt-get update`、`apt-get install` 或 `pip install -r requirements.txt`。依賴更新必須先建置新 image 並通過建置 workflow。
- GHCR 拉取失敗時 job 會在 steps 開始前失敗；先檢查 package 存在性、Actions 存取權及 `build-worker-image.yml` 的最近執行紀錄。

`deploy.bat` 會 `git add -A`、commit 並 push 當前 branch，屬大範圍發布工具。執行前必須先檢查 `git status`，確定所有刪除與機密檔排除都符合意圖；本需求書不要求自動執行部署。

## 3. 重試與恢復

- setup：catalog 最多 3 次，間隔 60 秒；Python dependencies 由預建 image 提供。
- worker：pipeline 整體最多 3 次；每次沿用 Workspace cache 與 checkpoint。
- 逐章：單章失敗會繼續其他章；批次尾端以 incomplete 集合決定 job 成敗。
- uploader：一般失敗最多 3 次；exit 75 立即保存為安全暫停，由排程日後 rerun failed job。
- dispatcher：每 15 分鐘以 GitHub queue 的 task ID/Run ID 檢查；執行中不重複啟動，`waiting_retry` 到安全時間才重跑同一任務。每次 Dispatcher 開始後刪除比自己更早且已完成的 Dispatcher Run 紀錄，避免 Actions 清單洗版。

cache restore 是最佳努力，不是資料庫保證。Actions cache 可能到期；發布安全性仍需依 YouTube playlist/channel 精確標題與已保存 Video ID 交叉恢復。

## 4. YouTube 錯誤分類與多專案輪替機制

- `quotaExceeded` (403)：API project 日配額。系統具備**多專案配額自動輪替 (Multi-Project Rotation)** 能力，依序使用專案 1 至 10；任一專案配額用盡時，自動無縫切換至下一專案繼續影片、縮圖、字幕與清單作業。每一輪全部失敗後由專案 1 重新開始，完整嘗試三輪；僅當 10 組專案三輪皆不可用時，才拋出 `UploadPaused` (exit 75)，以 `America/Los_Angeles` 的下一個午夜再加 15 分鐘為安全重試時間。
- `uploadLimitExceeded`：頻道 24 小時上傳限制（頻道層級防濫用限制，非 API 專案配額）。從錯誤時間起等待 24 小時 15 分鐘。
- thumbnail 429：保存 Video ID 與 pending thumbnail，暫停；下次先修補縮圖。
- caption/playlist 暫時失敗：保留 private 影片及 pending 項目，通常一小時後再試。
- authentication/invalid credential：不可無限重試；標 failed 並由維運者更新 secret。
- 未取得 Video ID：來源媒體不得刪除，Part 不得推進。


## 5. 觀測與判讀

- worker log 的 `[PROGRESS_MARKER]` 代表該章六 stage 完成。
- `[API_UPLOAD_MARKER] DONE` 代表該 Part 完成發布交易，不只 `videos.insert` 成功。
- `[API_UPLOAD_STATUS] PAUSED` 必須包含 uploaded/total/retry_at/source_run/reason。
- `[API_UPLOAD_STATUS] COMPLETE` 加上 state 無 pending 才是發布完成。
- Actions Job Summary 應呈現逐章 stage 表與發布 step 表；GUI 的綠色成功不得取代 server-side checkpoint 證據。
- production Run 名稱必須包含 workflow 用途、小說書名、章節範圍與永久 task ID（或 `GUI直接執行`）；Dispatcher Run 名稱必須明示為「有聲小說佇列調度」及觸發事件，不得只顯示內部 ID。

## 6. 常見故障定位

| 症狀 | 先檢查 | 恢復方式 |
|---|---|---|
| 目錄為空 | 網站 HTML、`/Book/Read/`/`/read/` selector、編碼 | 更新 parser 並加 fixture 測試 |
| TTS 有 WAV 無 SRT | TTS operation log、兩 stage checkpoint | 刪除/撤銷該組無效產物後重跑同章 |
| MP4 存在但重做 | ffprobe、音訊時長、checkpoint fingerprint | 修復壞檔或驗證規則，不可強制標完成 |
| worker 成功但不上傳 | `needs`、mp4 artifact 名稱、inventory | 補齊 artifact 或 rerun failed jobs |
| job 在 steps 前無法啟動 | GHCR package/tag、`packages: read`、image build run | 修復 package 權限或重跑 image build，不在 production job 改回 apt |
| YouTube 重複影片 | state run ID、精確 title、playlist/channel index | 停止新上傳，先修復 checkpoint 映射 |
| GUI 獨立上傳 404 | 缺少 `youtube_upload.yml` | 使用主 workflow 自動上傳，或完成第 07 章修正 |
| GUI 下載找不到 Release | 現行 workflow 無 Release job | 從 Actions artifacts 下載，或實作 Release 契約 |

## 7. 安全與資料保留

- `.env`、OAuth token/client secret 不得加入 Git；若曾提交應撤銷並輪替，不只刪檔。
- log 只可記錄 secret 名稱缺失，不得輸出值或 Authorization headers。
- 刪除本地/雲端媒體前，必須已持久保存 Video ID 且遠端驗證完成。
- 對 cache、artifact、Release 的清理要以明確 run/book 為範圍，禁止對 Workspace 根目錄做模糊遞迴刪除。

## 自動續作與停止條件

- Queue retry 不設 run attempt 上限；production run 未成功時由短時 dispatcher 依 `retry_at` 重跑該 task 的 failed jobs。
- 永久來源缺章顯示為 worker 綠色成功，同時輸出 `::warning` 與完整證據，不得靜默略過。
- timeout、429、5xx、防爬、解析器失效及媒體產製錯誤維持紅色失敗。
- 自動續作只在 publication checkpoint 顯示所有 Part 完成，且 YouTube 影片、縮圖、CC、播放清單與公開狀態均完成回讀後停止。
- 人工解除 `source_missing` 時，刪除對應 SourceStatus JSON 與該章 checkpoint 狀態後即可重新製作；既有 YouTube Part 不得自動覆蓋。


## 5. 跨 Run 產物繼承與 Cache 淘汰故障應變

1. **唯一紅 X 前手是第一順位**：每個新 Run 必須先使用調度器按 `book_profile_id` 鎖定的單一 `artifact_source_run_id`；來源必須是已結束、`conclusion=failure`、仍存在且有未過期必要 artifacts 的最新 Run。取消、暫停、執行中、成功、missing 或已刪除 Run 不得成為前手。
2. **禁止跨 Run 拼接**：鎖定後只能下載該來源的 `shared-config` 與對應 `video-worker-*`，不得再掃描更舊 Run，也不得同時重複下載 `mp4-worker-*`。下載最多重試 3 次。
3. **只補缺口**：來源中通過現行標準的逐章與階段成果必須沿用；只執行缺失、損壞或設定指紋不符的後續 stage。來源完全不可用或 3 次下載皆失敗時，允許直接使用精確 Cache 或重新製作，不得改抓另一個歷史 Run。
4. **不得無限回溯或模糊猜測 Run**：任何來源錯誤都不得觸發更舊 Run 下載；恢復失敗必須輸出明確 warning，然後依本節規則進入精確 Cache 或重新製作。
5. **Cache 隔離**：Cache key 必須包含 `book_profile_id`；GitHub 淘汰 Cache 只代表第二順位不可用，後續僅重做 artifact 與 Cache 都未提供的章節。
6. **CC 字幕自癒機制 (Self-Healing Subtitle)**：
   - 在發布驗收前若偵測到 YouTube CC 繁中字幕軌缺失，自動於 `Upload_Subtitles/`、`prepared_parts/` 等目錄定位對應 Part 之 `.srt` 檔案並自動補傳。
