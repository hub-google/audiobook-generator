# 04 資料與介面契約

## 1. `config.yaml`

```yaml
book_title: 凡人修仙傳
base_url: https://tw.hjwzw.com
catalog_url: https://tw.hjwzw.com/Book/Chapter/1644
start_chapter: 1
end_chapter: 10
total_available_chapters: 2442
chapters: [/Book/Read/1644,409280]
selected_indices: [1]
source_indices: [1]
chapter_titles: [第一章 開始]
chapter_title_by_index: {'1': 第一章 修正後名稱}
chapters_per_worker: 10
tts:
  engine: edge-tts
  edge_voice: zh-CN-YunxiNeural
  edge_rate: '+50%'
paths:
  workspace_base: Workspace
gdrive_folder_id: ''
```

契約：

- `book_title` 必須移除 `\ / : * ? " < > |`，並作為工作目錄及檔名前綴。
- `chapters[i]` 必須是 `selected_indices[i]` 的 URL；兩陣列長度不一致應立即失敗。
- `source_indices[i]` 是該章不可變的目錄 UUID；重新編號只改 `selected_indices[i]`，不得改 `source_indices[i]`。
- `chapter_titles` 與選取後的 `chapters` 等長；`chapter_title_by_index` 只保存 GUI 曾修改的輸出章號到完整標題映射，crawler 必須優先使用該值覆蓋網站頁面標題。
- `start_chapter/end_chapter` 表示原始目錄閉區間，不代表實際連續輸出；排除章以 `selected_indices` 為準。
- `chapters_per_worker` 必須與 matrix 計算後的 effective 值相同。
- 新建 config 必須寫 `edge_rate: '+50%'`；舊 config 缺欄位時 TTS 回退 `+0%`，以免舊快取被無聲改速。
- 相對 `workspace_base` 以儲存庫根目錄解析。

## 2. Matrix JSON

外型為 `{"include":[{"worker_id":0,"book_title":"...","start_chap":1,"end_chap":10}]}`。`start_chap/end_chap` 只供 job 名稱與 cache key；worker 的權威章節集合是 config 中相同 slice。worker ID 從 0 起且連續。

## 2.1 目錄解析與選章介面契約

`parse_catalog()` 必須保留目錄頁每一筆章節項目，並回傳等長的 `chapters` 與 `chapter_titles`。疑似重複項目不得在解析階段刪除；`duplicate_indices` 使用 1-based 來源索引標記後續重複項目。

章節標題在 GUI 中拆成下列衍生欄位，衍生欄位不取代原始 `chapter_titles`：

| 欄位 | 契約 |
|---|---|
| `UUID` | 原始目錄 1-based 固定流水號；建立後不受選取、排除或輸出重新編號影響，並作為改名與重複關聯鍵。 |
| `編號章節數` | 未重新排序時為來源索引；重新排序後為已選項目的連續輸出章號。 |
| `網站章節數正規化` | 僅正規化可辨識的開頭章節識別；中文／大寫中文／全形數字轉阿拉伯數字，並保留番外、序章、季、卷、集等結構。 |
| `網站顯示章節數` | 從網站原標題擷取的章節識別前綴，允許保留其顯示空格；NFKC 轉換造成的全形字元等價化除外。 |
| `章節名稱` | 去除章節識別前綴後的原名稱；其中數字不得受章號正規化影響。可雙擊原地編輯，保存後須依 UUID 寫入 `chapter_title_overrides`。 |
| `重複標記` | 依目前勾選的重複條件即時計算；「重複」文字可單擊開啟完整關聯明細。 |

重複比較的可選鍵為 `網站章節數正規化` 及 `章節名稱（去除空白）`。預設同時啟用兩鍵並採 AND 組合；只啟用一鍵時以該鍵比較；介面不得接受兩鍵皆停用。章節名稱去空白只供比較，不得改寫表格顯示文字或原始資料。

佇列任務的 `chapter_title_overrides` 是 `{UUID字串: 修正後完整章節標題}`。GUI dispatch 與 `queue_dispatcher.py` 必須將其序列化為 UTF-8 JSON、Base64 編碼後透過 workflow input `chapter_title_overrides_b64` 傳遞；`catalog_parser.py` 必須在重複分析、config 生成與 matrix 生成前依 UUID 套用。無效 Base64 或非 JSON object 必須拒絕；越界 UUID 必須忽略，不得錯套到其他章。

## 2.2 GitHub 雲端佇列狀態契約

`automation-state:audiobook-queue.json` 使用 schema version 2，頂層工作集合固定分為 `queue` 與 `completed`。`queue[*].position` 必須連續為 `1..N`；`completed[*]` 不得包含 `position`。成功任務必須以單次整檔寫入由前者搬至後者並立即補位，其他非成功終止或等待狀態仍留在 `queue`。完整狀態、寫入觸發及 GUI 契約以第 08 章為準。

## 3. 環境變數與 Secrets

| 名稱 | 使用位置 | 必要條件 |
|---|---|---|
| `GITHUB_REPO` | GUI | 雲端操作必要，格式 `owner/repo` |
| `GITHUB_TOKEN` | GUI | dispatch/cancel/poll/download 必要；不得提交 |
| `GEMINI_API_KEY` | metadata | 無有效 master cover 時的正式封面生成必要 |
| `HF_TOKEN` | metadata | 呼叫 FLUX 生圖必要 |
| `YOUTUBE_REFRESH_TOKEN` / `_1`~`_10` | uploader | YouTube 發布必要（支援 1~10 組多專案配額自動輪替） |
| `YOUTUBE_CLIENT_ID` / `_1`~`_10` | uploader | YouTube OAuth 必要（支援 1~10 組多專案配額自動輪替） |
| `YOUTUBE_CLIENT_SECRET` / `_1`~`_10` | uploader | YouTube OAuth 必要（支援 1~10 組多專案配額自動輪替） |
| `GH_TOKEN` | uploader/workflow | 下載來源 run artifacts 與 `gh` 查詢必要 |
| `FORCE_REGENERATE_MASTER_COVER=1` | metadata | 明確要求忽略有效 master cache 時才設定 |
| `ZIP_PASSWORD` | GUI | 現行傳入 workflow 但未被消費 |

根目錄 `.env.example` 目前只列 GitHub/Gemini，未完整涵蓋以上 secrets；部署時以 workflow secrets 為準。`.env`、`token*.json`、`client_secret*.json`、`client_secret/` 資料夾都視為機密，不得出現在 Git 版控、文件範例值、log 或 artifacts。

### 3.1 YouTube 多專案憑證管理契約 (2026-08-22 增補)
- 本地開發時，憑證放置於 `client_secret/client_secret_1.json` 至 `client_secret_10.json`，授權完成後自動產生 `client_secret/token_1.json` 至 `token_10.json`（向下相容根目錄單組檔案）。
- 執行 `python src/youtube_api_uploader.py --auth-pool` 可於本地瀏覽器依序對尚未完成授權之專案完成登入，並可自動透過 GitHub CLI (`gh secret set`) 將 Refresh Token 同步至雲端 Secrets。
- 正式 workflow 必須設定 `YOUTUBE_EXPECTED_ACCOUNT_COUNT=10`，缺少任一組 client ID、client secret 或 refresh token 時必須在上傳前失敗，不得靜默退回較小憑證池。


## 4. 檔案結構與命名

```text
Workspace/<書名>/
├─ RawText/<書名>_chapter_<N>_raw.txt
├─ CleanText/<書名>_chapter_<N>_clean.txt
├─ Audio/<書名>_chapter_<N>.wav
├─ Subtitles/<書名>_chapter_<N>.srt
├─ Images/<書名>_chapter_<N>.jpg
├─ Video/<書名>_chapter_<N>.mp4
├─ Checkpoints/worker-<ID>.json
├─ Cover/
│  ├─ master_cover.jpg
│  ├─ master_cover_prompt.json
│  └─ <書名>_process_log.txt
└─ Part_<NN>/
   ├─ youtube_title.txt
   ├─ youtube_description.txt
   ├─ youtube_cover.jpg
   └─ youtube_metadata.txt

Output/<書名>/
├─ <書名>_full.srt
└─ Parts/<書名>_Part_<NN>_Ch<SSSS>_to_Ch<EEEE>.mp4

Upload_Subtitles/
└─ <書名>_Part_<NN>_Ch<SSSS>_to_Ch<EEEE>.srt

upload_resume_state/state.json
```

章號解析以檔名 `_chapter_(\d+)` 為準。Part 檔的章號補足 4 位、Part 補足 2 位。程式不得依作業系統字典序推斷章序，必須轉為整數排序。

## 5. 逐章 checkpoint

路徑為 `Workspace/<書>/Checkpoints/worker-N.json`，schema 現行版本 2。記錄 worker、分配章節、六個 stage、status、attempts、時間、error、產物 metadata、resume_from 及 worker-level stages。

完成判定不是「檔案存在」：

- Raw/Clean text：可讀、非空、達最低內容門檻；clean 另檢查格式。
- WAV：RIFF/WAVE 可解碼、有 channel/sample rate/frames、時長合理。
- SRT：序號與時間格式有效、非空、時間遞增，末尾不得明顯超過 WAV。
- JPG：Pillow 可解碼，章節卡期望 1280×720。
- MP4：ffprobe 可讀、含 video/audio stream、時長與 WAV 相符。

寫 checkpoint 必須使用同目錄暫存檔、flush/fsync 後 `os.replace`，避免半寫 JSON。產物被修改或驗證失敗時，該 stage 及下游不得繼續顯示 completed。

## 6. 發布 checkpoint

預設路徑 `upload_resume_state/state.json`。必要欄位包括版本、來源 `run_id`、privacy、status、reason、retry_at、completed_titles、part_plan、playlist URL，以及四種 pending map。`PublicationCheckpoint` 另保存 normalized plan fingerprint、全域步驟與每 Part 發布步驟。

同一 state 只可續傳相同來源 run。Part plan 一旦鎖定，若新 inventory 得到不同 fingerprint 必須停止並要求顯式重建狀態，不能悄悄改分部導致標題或 Video ID 錯配。

`part_plan[*].duration` 是每個實際影片／Part 經媒體探測得到的秒數。播放清單正式標題的唯一計算契約為 `whole_hours = floor(sum(part_plan[*].duration) / 3600)`，輸出 `[已完結]《book_title》{whole_hours}小時 全集`；整數不得補前導零。`final_playlist_validation` 必須保存正式 `title` 與 `total_duration_seconds`，且正式改名只能發生在全部 Part 與使用者播放清單驗收成功之後。

## 7. GitHub Actions artifact/cache 契約

- `shared-config`：來源 run 的唯一設定事實。
- `mp4-worker-N`：發布所需 Video、Subtitles（及若存在 Upload_Subtitles）。
- `video-worker-N`：完整 Workspace，僅供保存與檢查，不應作為發布優先下載。
- worker cache：key 含書名、顯示章號範圍、worker ID、run ID、attempt；restore 使用穩定 prefix。
- publication cache：以來源 run ID 和 attempt 分代，內容含 state、Cover、Upload_Subtitles。

## 8. HTTP/CLI 介面

- GUI dispatch：`POST /repos/{repo}/actions/workflows/audiobook.yml/dispatches`，ref=`master`。
- GUI cancel：`POST /repos/{repo}/actions/runs/{run_id}/cancel`。
- worker：`python src/worker_pipeline.py --stage {pipeline|crawl|clean|tts|image_gen|video_gen|validate} --worker-id N [--config PATH]`。
- uploader：`python src/youtube_api_uploader.py (--run-id ID --repo OWNER/REPO | --input-dir DIR) --privacy {public|unlisted|private} --state-file PATH`。
- uploader exit 0 表示完成/無工作；75 表示安全暫停、需日後續傳；其他非零表示失敗。

## SourceStatus 契約

每章證據位於 `Workspace/<書名>/SourceStatus/chapter-<N>.json`，至少包含：

- `chapter`、`status`、`reason`、`updated_at`
- `observations[]`：`observed_at`、`run_id`、`run_attempt`、`http_status`、`url`、`final_url`、`title`、`fingerprint`
- 確認缺章時的 `confirmed_at` 與 `confirmation_count`

允許狀態為 `pending`、`source_missing_candidate`、`source_missing`、`available`。只有 `source_missing` 可作為 uploader 跳過章節的機器可讀證據。Part plan 必須保存 `source_missing_chapters`，且此欄位納入 plan fingerprint。
## 9. prepared-plan 與 HF merge artifact 契約

GitHub artifact 名稱固定為 `prepared-plan`，只包含：

- `config.yaml`：來源 Run 鎖定後的書名、選取章節及缺章設定。
- `parts-plan.json`：`schema_version`、`source_run_id`、`book_title`、
  `selected_indices`、`source_missing_chapters`、`chapter_artifacts`、依
  `part_num` 排序的 `parts` 及最多 17 筆的 `matrix.include`。

每一 Part 在 HF 的固定資料夾必須包含同 stem 的 `.mp4`、`.srt` 以及
`merge_manifest.json`。manifest 必須含 `status=merge_complete`、來源 Run ID、
Part plan、遠端路徑、bytes 與 SHA-256。publisher 必須逐檔驗證後才能呼叫 YouTube。

publisher 不得自行改寫章節歸屬；plan、HF manifest、檔名、雜湊或 config
不一致時必須在任何 YouTube 發布前失敗。
